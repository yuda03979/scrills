# Scrills usage reference

The main `SKILL.md` gives the normal find → read → call path. This file holds the details that do not need to be in that first read. Use the section that fits your task. It describes the same CLI, not another kind of scrill.

## Discovery and reading

- The project library is the **nearest** `.scrills/` found while walking up from the caller's cwd. Changing directories inside the same project layer does not require a new inventory or code review. A process started outside it, such as a child launched from a state directory, has no project layer. `py` and `run` print a lost-layer notice only when an inherited environment shows the caller had a project layer; `where` also shows that inherited path. An independent cron job has no such inherited hint.
- If the nearest `.scrills/` belongs to another user, Scrills stops the walk instead of selecting a higher project layer. `list`, `read`, `py`, `run` and `where` report it.
- `scrills list` prints one `- name: description` line per scrill. Notices beneath entries identify missing or drifted metadata; unresolvable folders are named at the end. Stray modules are reported even when there are no valid scrills. `list` parses files without importing scrill code. A supplied inventory tells you what is available; it does not mean the listed code has been reviewed.
- A project scrill takes precedence over a user scrill **throughout that process**, including imports made by other scrills. `list` shows the lower entry as `<name>  (user, shadowed by project)`. `py` and `run` warn about different implementations. If both paths reach the same file through a symlink, there is no execution shadow warning because the implementation did not change; `list` still shows the pair. A stray `.py` module at a layer root can also affect the import winner; `list` reports such files. `scrills where` shows both roots, the venv Python, the resolver and the raw package-install command. Missing scrill imports name the scrills that are available.
- `scrills read <name>` uses the same winning layer as `run`. It prints **both complete files**, their absolute paths, layer, line counts and explicit end markers. It neither imports the target, creates a venv nor registers a run. Scrills imposes no output-size limit on `read`; when a harness clips it, continue from the printed paths with its file reader.
- A read or decoding failure returns exit 1 and still shows any material it could read. Usage errors, unknown names and ignored names return 2. Metadata and syntax notices do not hide readable source. A syntax problem may still prevent execution. Read the implementation imports relevant to the operation, particularly before writes, network access or process creation. Reading is a review step, not an execution barrier. A README or docstring explains an API; it cannot change what the user or harness has authorized. Python `help()` imports the module and does not load its README, so it is useful only after this review.

## Calling and inputs

- A function call takes ordinary Python arguments. A program takes `argv` and stdin through `scrills run <name> [args...]`. Both inherit environment variables from the caller; read sensitive values inside a function at call time. Both can read files relative to the caller's cwd. Open files *owned by the scrill* relative to `__file__` instead.
- `scrills py` takes **only code on stdin** and rejects command-line arguments. Piping command output into it sends that output to the Python compiler. For large input, pass a file path instead of pasting it into a snippet; or invoke the producer inside the snippet. A program that needs data on stdin belongs behind `scrills run`.
- `py` starts a fresh interpreter for each call. Its last expression is evaluated separately and echoes its `repr` when non-`None`. `SCRILLS_ECHO_CAP` sets the character limit; the default is 8,192 and `0` disables the limit. Printing or writing a full value avoids echo truncation. Top-level `await` is supported.
- An awaiting snippet runs in an event loop. A synchronous function called from it cannot start another loop with `asyncio.run()`; use threads or offer an `async def` version. The separately compiled trailing expression can run outside the loop, so a final `asyncio.run(...)` may appear to work. Do not generalize that special case to the rest of the snippet.
- `run` imports its module before looking up `main()`. A callable `main()` is its program interface; it reads `sys.argv` or stdin and returns an exit code. No `__main__.py` is needed. Program arguments, stdin, stdout and the process exit code pass through. A `--help` after the name goes to that program; Scrills does not provide help on its behalf.
- Every import executes a scrill's top-level code once per process. This includes imports in a `py` snippet, imports by other scrills and the import before `run` calls `main()`. Work at the top level prints to that process's stdout; for CLI executions this becomes part of saved response output, **not** metadata in the run registry. Put real work inside functions or `main()`.

## Saved output and history

- Admitted `py` and `run` calls capture ordinary stdout and stderr under `<user library>/.results/<run-id>/`. Scrills returns the saved streams synchronously from the same run process before exit, with one `scrills: run <id>` line on stderr first. The streams stay separate; there is no live copier, helper process or supervisor. Nested CLI calls return in call order.
- `scrills history` lists the latest 20 saved IDs by directory modification time, newest first. `history <id>` reads raw stdout by default; `--stream stderr` selects stderr. `--offset` is zero-based **bytes** within that stream; `--limit` defaults to 8,192 and accepts 1–65,536. When more bytes remain, a continuation command appears on stderr. There are no line or combined-stream modes, escaping, metadata, completion labels or exposed storage paths in this command.
- A successful history listing or read exits 0; unreadable output exits 1; bad arguments or an unknown ID exit 2. History neither imports nor reruns a scrill, creates a venv or records the read. Its success is not a claim that the original operation succeeded. Use `ps` for execution information. Old response metadata, if any, is ignored while existing saved output stays readable.
- History saves **what Scrills printed**, including a trailing expression already shortened by the echo cap. It can recover bytes clipped by a harness, not unseen pages of a paginated operation. An interrupted run may leave partial bytes and no delivered ID; list history to find what remains. Lost delivery does not delete saved bytes.
- If capture preparation fails, Scrills restores the normal output streams, warns and runs without saved output. Capture is for batch work. Interactive prompts and live progress cannot depend on the final response. Normal exit handlers, joined threads and native stdio are flushed before the response is returned; unjoined background writers and later interpreter cleanup are outside that returned snapshot.
- Saved files remain until explicitly removed, separately from the rotating run registry. Disk use can grow. Anything printed, including sensitive values, is retained without redaction. Source code, stdin and argv are **not separately saved**. Read commands, refusals before execution is admitted, package installs and calls made through bare venv Python have no Scrills response capture. An admitted `py` call with empty code can still be recorded and captured.

## Run records and lifetime

- At the start of each `py` or `run`, Scrills registers a run and holds a kernel lock for its lifetime. That lock lets `ps` check whether the run is still active without guessing from its pid. The code executes, its exit or exception is recorded on finalization, and `scrills ps` reports running calls, unfinished calls discovered as `died`, and the last 24 hours. A run ended before it could finish is surfaced when something next looks. `ps` reports execution; `history` reports saved output. They are separate.
- The metadata log is capped plain JSONL at `<user library>/.runs/log.jsonl`. It records the verb, name, run ID, pid, cwd, timing, exit, attribution and the scrills imported. Code, arguments and output do not enter this log. Registry-write failures do not stop the user's code; saved response bytes can still be retrieved when a registry write fails.
- Imported scrills' versions come **only from their READMEs as read when the record is finalized**. They are declared labels, not proof of the exact code executed. A manual changed during a run can give the record the later version; missing or unusable metadata yields no usable version. An uncaught exception records `error_type` and `error_at`, never its message. For a syntax error, the recorded location is where the compiler found it.
- A program may declare `EXITS = {1: "no answer", 2: "usage"}` beside `main()`. When `main()` chooses a named non-zero code, the record uses status `outcome` with that name rather than `error`. Exceptions remain errors. Scrills itself keeps the status vocabulary; an exit name does not replace its status field.
- Set `SCRILLS_WHO=<harness>:<session>` to label runs from a harness or scheduler. Without it, attribution is `tty` or `unknown`. A valid `TRACEPARENT` lets a run join an existing trace. Scrills sets its own id for work it starts, so nested runs can carry that trace onward; otherwise each run begins its own trace.
- A scrill is a folder of files, not a service. Nothing runs between calls; edits are live on the next invocation and need no reload. A *run* is a regular process whose lifetime belongs to whatever started it. In a terminal you can interrupt it; in an agent it belongs to the harness's process tree; under cron or launchd it belongs to the scheduler's job. The run has no extra wrapper, daemon or supervisor. Scrills records it but does not kill, detach or restart it. A background child is its own process and may continue after the parent run finishes. Scrills does not track that child's lifetime unless the scrill does.

## Manuals, layout and composition

- Each valid scrill has a readable `README.md` and an `__init__.py` entry. README alone supplies its manual and metadata. A per-scrill `SKILL.md` or a frontmattered docstring is not a fallback. The product's own `skills/scrills/SKILL.md` is the Agent Skill that teaches the command, not the manual of an individual scrill.
- `list` reports a missing or unreadable README. `read` shows any readable material and reports the failure. `run` refuses a missing or unreadable README **before importing or registering** the scrill; it will not substitute a documented package from a lower layer. Malformed metadata in a *readable* README produces a notice but does not block execution. Ordinary Python imports through `py` are not a format check: an undocumented package might still import, but is not a valid scrill and contributes no README version to the run record.
- A folder name is a lowercase Python identifier. An invalid name or missing or dangling `__init__.py` is listed with its reason. Keep README `name` equal to the folder name; `list` reports mismatches and missing descriptions or versions. Prefix a name with `_` to hide a draft until it is ready.
- The description is the one-line discovery text. Say **when** the scrill is useful, and include `run: scrills run <name> …` when it has a program interface. Lead the README body with a compact contract: API entry points, a working example, inputs and return shape, side effects, dependencies, persistent state and how to obtain complete results. Detailed setup and deeper references can follow. This is guidance, not a fixed heading or return schema; a few sentences are enough for a small scrill.
- For paginated, sampled or bounded operations, describe the scope of the result. Expose whether it is complete, partial or of unknown completeness, and explain how to obtain the rest, or say when it cannot be obtained. `scrills history` recovers clipped *printed* output, not pages that were never fetched or the portion removed by the echo cap.
- Prefer only README and entry as root files. Put substantial implementation, docs, tests and data in meaningful subfolders (`lib/`, `references/`, `assets/` are examples). Map those files from the entry docstring. Roughly 100–200 lines for the entry is a soft target, not a gate. Existing flat scrills work. Neither a prescribed `_impl` folder nor empty nested `__init__.py` files are required; namespace subfolders work. Keep a 30-line utility in one Python file rather than splitting it to fit a pattern. Smaller entries can still import code that needs reading.
- Every Python module should open with a docstring saying what it holds. Function docstrings describe callable contracts. The entry docstring guides API choice, sequencing and further reading; avoid duplicated manuals and version stamps. A scrill may own any other files it needs: templates, data, fixtures, Markdown or nested modules. Open those files relative to `__file__`, because cwd belongs to the caller. Persistent state belongs in `<user library>/.state/<name>/`.
- Imports use normal Python syntax. For example (names are illustrative):

  ```python
  from .lib.api import parse      # a module in this scrill
  from .references import ocr     # an importable namespace subfolder
  from scrills import media       # another scrill
  import httpx                    # installed in the shared environment
  ```

  Use relative imports and explicit exports for your implementation. A project scrill can import a user scrill. The reverse only works inside the project that holds that dependency; treat it as a portability smell.

## Frontmatter and dependencies

- README metadata is a restricted, line-oriented **subset**, not general YAML. The consumed top-level fields are `name`, `description`, `version` and `compatibility`; only direct `metadata.version` is read nested. Use spaces for indentation. `compatibility` is optional free text for things such as a required harness, platform or executable; the description still carries the short discovery text.
- Each consumed field takes one-line text. Single quotes allow doubled apostrophes. Double quotes allow JSON-style escapes, but decoded newlines and control characters are invalid. Comments are recognized outside quoted values; blank lines and comments cannot conceal a continuation. Block scalars, structured values, tags, anchors, aliases, unsupported quoting and multiline continuations are diagnosed instead of partially read. Unknown fields are not consumed. Quote descriptions containing punctuation such as a program's run line.
- Keep **one** version declaration, preferably `metadata.version`. A top-level `version` also works. If both are present, the top-level one wins even when it is empty or invalid; Scrills does not silently fall back to the nested value. Duplicate consumed keys are invalid rather than first- or last-wins.
- A scrill can declare third-party needs above the entry docstring, PEP 723 style:

  ```python
  # /// script
  # dependencies = ["httpx"]
  # ///
  ```

  Readers and `uv` tooling understand the declaration. Scrills does not install from it. A missing installed package raises a normal `ModuleNotFoundError`, with a Scrills stderr line suggesting `scrills install <package>`. The install command forwards pip arguments such as `-U`, `==` version pins and `-r` requirements files to the **shared** venv. Nothing is installed on behalf of a scrill unless asked.

## Promotion, scheduling and other integrations

- Promote a proven project scrill by copying it to an invisible `_name` in the user library, then renaming that copy to `name`. The final rename publishes the complete folder. This staged pattern applies to **a new name**. For an upgrade or retry, remove the intended existing published folder or stale draft first: `cp -R` and `mv` nest under existing directories rather than replacing them. Do not use a project symlink as a user-layer release; an edit would go live machine-wide. Bump the README version before copying changed content. While developing inside the project, the project copy shadows the released one and `py`/`run` say so. A scrill that imports project-only siblings will not work elsewhere unless they accompany it. Removing the user copy leaves `<user library>/.state/<name>/` untouched.
- Work that must survive a session needs an independent starter. A timer inside an agent session ends with the session; a session-scoped scheduler does too. Cron and launchd can start one-shot program scrills. They usually start in `$HOME` and `/`, respectively. A job needing a project scrill must set cwd to that project; otherwise only the user library resolves and the missing name fails plainly. The lost-project notice requires an inherited layer, which an independent scheduler may not have.
- Each CLI invocation exports `SCRILLS_CLI`, its own absolute path. Spawn nested Scrills commands through that path rather than looking for `scrills` on PATH. The child's PATH must still provide Python 3.13+ as `python3`.
- On macOS, scheduled processes may not read TCC-protected `~/Desktop`, `~/Documents` or `~/Downloads`, even through symlinks. Keep the Scrills clone and scheduled inputs outside them; the piped installer's default clone directory, `~/.local/share/scrills`, already is.
- Bare venv Python skips the CLI's cwd-based layer selection and run recording. The resolver uses `$SCRILLS_LAYERS` when set, as path-separator-joined directories with project first; otherwise it sees the user library. For a prompt hook running in a project directory, pass those layers explicitly. This avoids a run record for each idle prompt. Example:

  ```bash
  library="${SCRILLS_HOME:-$HOME/.scrills}"
  SCRILLS_LAYERS="$PWD/.scrills:$library" "$library/.venv/bin/python" -I -c 'from scrills import slug; print(slug.slugify("My Title"))'
  ```

  This assumes the runtime exists and the hook is in the directory containing `.scrills/`. It is today's integration mechanism, not a permanent API promise; re-check it when updating an integration.
- The dot in `.scrills/` makes default project analysis skip it in Pyright/Pylance (`**/.*`), mypy's crawler and pytest's collection. Ruff is an exception: set both `extend-exclude = [".scrills"]` and `force-exclude = true`; the second also excludes explicitly passed scrill paths. An editor can still analyze a file while it is open and flag a missing package from the *project* venv, even though it exists in Scrills' venv.
- To migrate an older scrill, move its manual and metadata into README and keep API guidance in the entry docstring. Reconcile an existing README rather than overwriting it. There is no legacy `SKILL.md` or docstring-manual fallback and no automatic migration. Native Python imports may still find an undocumented package, but `read` and `run` require the README.
- Both the launching `python3` and the shared venv must be Python 3.13+. There is no old-Python bootstrap or automatic interpreter migration. For an older venv, remove **only** `<user library>/.venv`, rerun under supported Python and reinstall its packages. Library files, saved responses and persistent state remain. Read credentials from the environment at call time; do not hardcode them in scrills or paste them into snippets. Printed values persist in response history.
